# NoteforJun 사용성 개선 설계 문서

작성일: 2026-09-13
대상 버전: v1 출시 이후 첫 수정
선행 문서: [2026-09-11-noteforjun-design.md](2026-09-11-noteforjun-design.md)

## 1. 배경

v1을 실제로 쓰면서 나온 수정 요청 7건을 다룬다. 새 기능을 늘리는 작업이 아니라, **이미 있는 기능이 손에 걸리지 않는 지점**을 고치는 작업이다. 선행 문서의 설계 원칙(자유도를 없애는 것이 기능이다 / 이 앱에서만 통하는 것을 배우게 하지 않는다)은 그대로 유효하며, 이 문서의 어떤 항목도 그 원칙을 바꾸지 않는다.

7건 중 2건(5번 재시작 복원, 7번 서식 팝업 Tab)은 **기능이 없어서 생긴 문제가 아니다.** 코드에 이미 구현돼 있고, 그 구현이 사용자의 기대와 어긋나거나 실제로는 동작하지 않는다. 그래서 고치는 자리가 "새로 만들기"가 아니라 "규칙 교체"와 "원인 제거"다.

## 2. 항목별 설계

### 2.1 메모 창 항상 위 고정

**문제**: 다른 프로그램을 클릭하면 메모가 그 뒤로 숨는다. 포스트잇으로 쓰는 앱인데 보려면 매번 찾아와야 한다.

**설계**: `windows.rs`의 `open_note`와 `open_list` 빌더 양쪽에 `.always_on_top(true)`를 더한다.

**토글을 만들지 않는 이유**: 토글은 ⋯ 메뉴 항목 하나, `note.json` 필드 하나, 창 생성 경로와 변경 경로 두 곳을 늘린다. "항상 보이는 포스트잇"은 이 앱의 전제이므로 끌 수 있게 만들 이유가 없다.

**목록 창도 포함하는 이유** (최초 설계에서 뒤집은 결정): 처음에는 목록이 넓어서 화면을 계속 덮는다는 이유로 제외했다. 그런데 그러면 목록이 메모 창과 겹치는 자리에 뜨는 순간 **영영 뒤에 갇힌다** — 항상 위 창은 일반 창의 포커스로 넘을 수 없어서, 목록을 클릭해도 앞으로 나오지 못한다. 목록은 메모를 지울 수 있는 유일한 화면이므로, 닿지 못하면 메모를 줄일 방법 자체가 사라진다. 넓어서 거슬리는 것은 × 로 닫으면 되지만, 갇힌 창은 되돌릴 방법이 없다.

### 2.2 기본 글자 크기

**설계**: `tokens.css`의 `--nfj-body-size`를 `14px`에서 `15px`로 바꾼다.

본문만 바꾸고 제목(`--nfj-h1-size` 19px), 상단바 제목칸(`--nfj-title-size` 14px), 목록 미리보기(`--nfj-preview-size` 12px)는 건드리지 않는다. 요청이 "기본 글자 크기"였고, 나머지를 같이 올리면 상단바 높이(34px)와 목록 행 높이가 함께 흔들린다.

### 2.3 한글 입력이 한 박자 늦는 문제

**증상**: 화면 왼쪽 위에 작은 조합창이 뜨고, '가'를 치면 그 조합창에만 '가'가 보이다가 다음 글자를 칠 때 비로소 본문에 '가'가 들어간다. 현재는 재현되지 않는다(2026-09-12에 한 번 관찰).

**진단**: 재현되지 않으므로 원인을 단정하지 않는다. 다만 코드에서 **조합 중에 매번 반복되는 낭비**를 하나 확인했다. `editor.js`의 `onUpdate`가 문서가 바뀔 때마다 `editor.getHTML()`로 문서 전체를 HTML 문자열로 직렬화한다. 한글은 조합 중에도 자모마다 문서가 바뀌므로 '가' 한 글자에 두 번 돈다. 메모가 길어질수록 이 비용이 커지고, IME 조합 타이밍을 밀어낼 수 있다.

좌상단 조합창 자체는 WebView2가 캐럿 위치를 IME에 보고하지 못할 때 나타나는 것으로, 앱 코드에서 직접 고칠 수단이 없다.

**설계**: 조합 상태를 보지 않는다. **직렬화 자체를 저장 시점으로 미룬다.** 타이핑은 신호만 보내고(`onUpdate`의 타입이 `(html) => void`에서 `() => void`로 바뀐다), `getHTML()`은 저장 직전 `note.js`의 `persist()`에서 한 번만 한다.

> 이 설계는 구현 중에 바뀐 것이다. 처음에는 "조합 중(`editor.view.composing`)에는 건너뛰고 끝난 뒤 한 번"으로 적었으나 쓰지 않았다. `compositionend` 시점에 ProseMirror가 마지막 글자를 문서에 이미 반영했는지 확신할 수 없고(ProseMirror는 한 박자 뒤에 DOM을 훑는다), 추측이 틀리면 마지막 글자를 잃는다. 코드베이스에 `composing`이나 `compositionend` 처리는 없다 — 찾지 말 것.

**이 방식이 안전한 이유**: 모든 저장 경로(타이핑 디바운스·제목·색·창 이동·닫기)가 `persist()` 한 지점을 지나고, `persist()`는 호출되는 그 순간의 문서를 읽는다. 디바운스 타이밍과 무관하게 저장되는 것은 언제나 화면에 있는 그대로이므로, 글을 잃을 경로가 구조적으로 없다.

이 수정은 증상이 다시 나타나지 않더라도 그 자체로 옳다. 실제로 존재하는 낭비를 없애는 것이지, 추측으로 다른 곳을 건드리는 것이 아니다.

**한계를 분명히 한다**: 이것으로 증상이 사라진다고 보장할 수 없다. 재발하면 그때 WebView2 쪽 원인을 따로 추적한다.

### 2.4 창 이동 손잡이 키우기

**문제**: 상단바 가운데 손잡이가 잘 잡히지 않는다.

**설계**: `note.css`의 `#grabber`를 다음과 같이 바꾼다.

| 항목 | 현재 | 변경 |
|---|---|---|
| 잡히는 영역 | 56 × 13px | 80 × 20px |
| 보이는 선 | 40 × 3px | 44 × 4px |
| 선 진하기 | opacity 0.38 | opacity 0.5 |
| 커서 올렸을 때 | 변화 없음 | opacity 0.75 |

**폭을 80px로 제한하는 이유**: 손잡이는 제목 입력칸 위에 겹쳐 떠 있고 `cursor: grab`을 쓰므로, 넓힌 만큼 제목을 클릭할 수 없는 구간이 된다.

구체적으로, 2.6의 `?` 버튼까지 들어간 뒤 창 최소 폭 220px에서 제목칸은 48px이고 그중 20px을 손잡이가 덮는다 — 제목을 실제로 클릭할 수 있는 폭은 28px이다. 기본 폭 460px에서도 제목칸 한가운데 80px이 드래그 영역이라, 쓴 제목 가운데를 클릭해 커서를 놓으려 하면 창이 끌린다. 80px은 이미 넉넉한 쪽이고 더 넓힐 여지가 없다.

**높이를 20px로 제한하는 이유**: 상단바가 34px이고 손잡이는 `top: 0`에서 시작한다. 높이를 더 키우면 상단바 아래쪽까지 덮는데, 그 구간은 지금 `#titlebar`의 `data-tauri-drag-region`이 맡고 있어 어차피 끌린다. 늘려봐야 얻는 것이 없고 제목 클릭 영역만 줄어든다.

커서를 올렸을 때 진해지는 것은 "여기가 잡는 곳"이라는 신호다. 크기만 키우면 여전히 어디를 노려야 하는지 눈에 안 들어온다.

### 2.5 재시작 복원 규칙 교체

**현재 동작**: `windows.rs`의 `startup_plan`은 `window.visible`이 참인 메모를 복원하고, 하나도 없으면 빈 메모를 한 장 내민다. `visible`이 거짓이 되는 경로는 × 버튼(`hide_note_window`)뿐이다.

**확인한 사실**: 저장된 메모 10건 중 `visible: true`는 2건, 나머지 8건은 `false`다. 즉 코드는 설계대로 동작하고 있고, 그 설계가 기대와 어긋난다. × 를 "잠깐 치우기"로 쓰는데 코드는 "그만 보기"로 해석한다.

**새 규칙**:

> 내용이 있는 메모를 **[화면에 떠 있던 것 먼저, 그다음 `updatedAt` 최신순]** 으로 정렬해 **최대 5개**까지 띄운다. 띄울 것이 하나도 없으면 빈 메모를 한 장 만든다.

- **빈 메모 제외**: 제목과 본문이 둘 다 비어 있는 메모(`is_blank`)는 복원 대상에서 뺀다.
- **5개 상한**: 메모는 계속 쌓인다. 상한이 없으면 지금은 9개, 한 달 뒤엔 수십 개의 창이 부팅 때 한꺼번에 뜬다.
- **떠 있던 것 우선**: `visible: true`를 최우선 정렬 키로 두어, 실제로 화면에 있던 메모가 상한 5개를 먼저 차지한다.
- **빈 메모 폴백 유지**: 이 앱은 창 테두리도 트레이 아이콘도 없다. 창이 하나도 없으면 앱은 켜져 있는데 사용자가 닿을 방법이 사라진다.

**구현 형태**: `startup_plan`은 순수 함수로 유지한다. 지금은 `Vec<String>` 두 개를 받지만, 새 규칙은 메모별로 (id, 떠 있었는지, 비었는지, 수정 시각) 네 가지가 필요하므로 입력 타입을 그에 맞게 바꾼다. 파일 시스템과 Tauri 핸들은 여전히 호출하는 쪽(`restore_all`)에 둔다. 그래야 규칙을 Rust 단위 테스트로 그대로 검증할 수 있다.

**바뀌지 않는 것**: `hide_note_window`는 지금처럼 `visible: false`를 저장한다. 그 값은 이제 "다음에 띄우지 마"가 아니라 "화면에 있지 않았다"는 사실 기록으로만 쓰인다. 작업표시줄 아이콘을 눌렀을 때의 동작(`open_blank`)도 바꾸지 않는다.

**부작용을 분명히 한다**: 이제 × 로 닫은 메모도 최근 5개 안에 들면 다음 부팅에 다시 뜬다. 요청에 따른 의도된 변화다.

### 2.6 `?` 도움말

**설계**: 상단바 `⋯` 왼쪽에 `?` 버튼을 넣는다. 커서를 올리거나 **초점이 닿으면** 안내가 뜬다. 마우스를 치우거나 초점이 떠나면 사라진다.

초점으로도 열리게 하는 이유는 이 버튼이 키보드만 쓰는 사람에게도 닿아야 하기 때문이다. 다만 **정방향 Tab으로는 닿지 않는다** — `note.js`의 제목 입력칸 처리가 Tab을 가로채 본문으로 보내므로, 정방향 Tab은 `+` → 제목 → 본문 세 칸을 돈다. `?`에 닿는 길은 본문에서 Shift+Tab(→ `×` → `⋯` → `?`)이다. `⋯`와 `×`도 원래 같은 처지다.

> 처음에는 "이 앱이 이미 제목 → 본문 → 서식 팝업을 Tab으로 잇고 있어서 `?`만 마우스 전용이면 그 흐름이 끊긴다"고 적었는데, 사실이 아니었다. 정방향 Tab 흐름은 애초에 `?`를 지나가지 않는다. 기능 자체는 그대로 두되(키보드로 닿는 길은 필요하다) 근거를 바로잡는다.

**내용**:

```
[] 또는 - 다음 스페이스   →  할 일 박스
# 다음 스페이스           →  제목
Ctrl+B / I / U            →  굵게 / 기울임 / 밑줄
글자를 끌면               →  형광펜 포함 서식 팝업
Ctrl+Alt+N                →  새 메모
```

"+ 스페이스"라고 쓰지 않는 이유는 상단바에 이미 `+` 버튼(새 메모)이 있어서, 안내에 나온 `+`가 그 버튼으로 읽히기 때문이다.

`- `를 같이 적는 것은 `rules.js`의 `TASK_INPUT_RULE`이 `[] `와 `- ` 둘 다 받기 때문이다. 실제로 되는 것을 적지 않으면 안내가 아니라 반쪽짜리 문서가 된다.

**`title` 속성을 쓰지 않는 이유**: 브라우저 기본 툴팁은 줄바꿈이 안 되고, 뜨기까지 1초 이상 걸리며, 키보드 초점으로는 열리지 않는다. 위 표를 보여줄 수 없다.

**상단바 폭**: 창 최소 폭이 220px이고 상단바에는 이미 `+`, 제목칸, `✓`, `⋯`, `×`가 있다. `?` 버튼은 다른 버튼과 같은 28px을 쓰고, 제목칸은 `flex: 1 1 auto; min-width: 0`이라 그만큼 줄어든다. 제목칸이 좁아지는 것은 받아들인다 — 최소 폭에서도 제목은 여전히 읽고 쓸 수 있다.

### 2.7 서식 팝업 Tab

**문제**: 글자를 끌어 서식 팝업이 떴을 때 Tab을 누르면 버튼 사이를 도는 게 아니라 밖으로 나간다.

**진단**: `bubble.js`는 **팝업 안에서의 순환만** 처리한다(마지막 버튼에서 Tab → 첫 버튼, 첫 버튼에서 Shift+Tab → 마지막 버튼). 이 코드는 단위 테스트도 통과한다. 빠진 것은 그 앞 단계, **본문에서 팝업으로 들어가는 첫 Tab**이다. 지금은 이것을 브라우저 기본 탭 순서에 맡기고 있다. 팝업이 `#shell` 맨 끝에 붙어 있어서 "우연히" 본문 다음 차례가 되는 구조이고, DOM 순서가 바뀌거나 WebView2의 탭 처리가 다르면 조용히 깨진다.

**설계**: 본문에 Tab 키 처리를 붙여, 팝업이 떠 있을 때 Tab을 가로채 팝업 첫 버튼으로 초점을 보낸다. 팝업이 떠 있지 않으면 가로채지 않는다(기본 탭 이동을 그대로 둔다).

이렇게 하면 세 구간이 모두 명시적으로 연결된다: 본문 → 팝업 첫 버튼 → (순환) → Esc로 본문 복귀.

**기존 코드는 건드리지 않는다**: 팝업 안 순환과 Esc 처리는 그대로 둔다. 고장난 곳이 아니다.

## 3. 검증

### 3.1 자동 테스트

| 대상 | 방식 |
|---|---|
| 2.5 복원 규칙 | Rust 단위 테스트. 빈 메모 제외, 5개 상한, 떠 있던 것 우선, 전부 비었을 때 폴백 |
| 2.7 본문 → 팝업 인계 | JS 테스트. 팝업이 떠 있을 때 본문 Tab이 가로채지고 첫 버튼으로 초점이 가는지 |
| 2.3 조합 중 저장 건너뛰기 | JS 테스트. 조합 중에는 `onUpdate`가 불리지 않고, 조합이 끝나면 불리는지 |

기존 테스트는 모두 그대로 통과해야 한다.

### 3.2 실제 앱 확인

다음 항목은 자동 테스트로 확인할 수 없다. `npm run tauri dev`로 앱을 띄워 눈으로 확인한다.

- 2.1 다른 프로그램을 클릭해도 메모가 앞에 남는가
- 2.2 본문 글자가 한 단계 커졌는가
- 2.3 한글 입력이 매끄러운가 (좌상단 조합창이 뜨지 않는가)
- 2.4 손잡이가 손에 걸리는가
- 2.5 앱을 껐다 켰을 때 내용 있는 메모가 최대 5개 돌아오고 빈 메모는 안 뜨는가
- 2.6 `?`에 커서를 올렸을 때와 Tab으로 닿았을 때 안내가 뜨는가
- 2.7 글자를 끈 뒤 Tab을 네 번 눌러 형광펜을 지나 굵게로 돌아오는가

**실행 전 준비**: 설치본이 실행 중이면 먼저 종료해야 한다. `lib.rs`의 `tauri_plugin_single_instance`가 앱 식별자로 중복 실행을 막으므로, 설치본이 켜져 있으면 개발 빌드는 뜨자마자 종료되고 설치본에 빈 메모만 하나 추가된다. 개발 빌드는 설치본과 같은 메모 폴더(`%APPDATA%\NoteforJun\notes`)를 쓴다.

실제 앱 확인은 작업 중 여러 번 나누지 않고, 코드와 자동 테스트가 모두 끝난 뒤 한 번에 몰아서 한다. 그래야 작업하는 동안 설치본을 반복해서 끊을 일이 없다.
